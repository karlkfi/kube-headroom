Headroom is a Kubernetes controller that sets container CPU limits from node slack, using the in-place pod resize API. It is CPU-only and opt-in per namespace.

> [!WARNING]
> **Limits now move when settings change, not only on scheduling events.** After this upgrade a `HeadroomConfig` edit can resize every managed pod in the cluster at once, and enrolling a namespace or adding a LimitRange resizes that namespace's pods. Nothing bounds that burst beyond the existing rate limits. See **Upgrading** before flipping `dryRun` on a large cluster.

> [!CAUTION]
> **Pods with pod-level `spec.resources` are now unmanaged on every Kubernetes version.** A new one gets no birth limit and no resizes, so if it has no pod-level CPU limit, any container without a CPU limit has no CPU ceiling at all. An existing one keeps whatever limit it has until it is recreated.

## Highlights

- **[Limits follow settings on quiet nodes](https://github.com/karlkfi/kube-headroom/pull/126).** In v0.1.0, flipping `dryRun`, enrolling a namespace or setting `max-cpu` did nothing until another pod landed on the node.
- **[Events are stored](https://github.com/karlkfi/kube-headroom/pull/124).** The v0.1.0 role granted core `events`, but the recorder writes `events.k8s.io`, so the API server rejected `CPULimitAdjusted` and every refusal event on every install.
- **[Full nodes shrink the pods they should](https://github.com/karlkfi/kube-headroom/pull/121).** A pod whose memory request equals its limit used to be refused, and the refusal stopped every pod after it on that node. It now stops one quantum above its request.
- **[LimitRanges cap raises](https://github.com/karlkfi/kube-headroom/pull/124).** A raise past a CPU `max` or `maxLimitRequestRatio` used to fail outright and blame a ResourceQuota. It now stops at the cap, and refusals name the object that refused.
- **[Native sidecars resize](https://github.com/karlkfi/kube-headroom/pull/122).** A managed pod with a CPU-requesting native sidecar was refused on every resize, on any node.
- **[Pods under a VPA that writes CPU limits are left alone](https://github.com/karlkfi/kube-headroom/pull/128).** A default-mode VPA and Headroom used to overwrite the same limit. Headroom now skips those pods with one `VPAManagesLimit` warning; a `RequestsOnly` or `updateMode: Off` VPA stays compatible.

## Upgrading

Requires Kubernetes 1.35 or later, and cert-manager unless you bring your own webhook certificate. Upgrade the CRD chart first:

```sh
helm upgrade --install kube-headroom-crds \
  oci://ghcr.io/karlkfi/charts/kube-headroom-crds --version 0.2.0

helm upgrade --install kube-headroom \
  oci://ghcr.io/karlkfi/charts/kube-headroom --version 0.2.0 \
  --namespace kube-headroom-system --create-namespace
```

Pass the same values you installed with.

Nothing stops the upgrade if you skip the checks below, so they are yours to run. `helm upgrade` also returns before the rollout finishes, so run `kubectl -n kube-headroom-system rollout status deploy/kube-headroom-controller-manager` afterwards. The rolling update needs 10m free for one extra manager pod: on a single-worker kind cluster with that worker full, it stayed Pending and the old manager kept running on the new role until capacity freed up.

1. **Check the RBAC change.** The manager's ClusterRole gains `create` and `patch` on `events.k8s.io` `events` and loses them on cluster-wide core `events`. Leader election keeps core `events` in the manager's namespace. On `verticalpodautoscalers` the role narrows from `get`, `list` and `watch` to `list`, which works whether or not the VPA CRD is installed. If you review or mirror this role elsewhere, update your copy.
2. **Check alerts on `quota-denied`.** `headroom_resizes_total{result="quota-denied"}` now means a ResourceQuota refused. A LimitRange refusal is `limitrange-denied` and any other 403 is `forbidden`, so an alert on `quota-denied` stops firing for those.
3. **Expect `CPULimitAdjusted` events to start.** They were rejected before, so anything watching events sees them for the first time.
4. **Find pods with pod-level resources.** Read **Pods with pod-level resources** below, and decide whether to close the uncapped shape.
5. **Find VPAs on managed workloads.** Any VPA in a managed namespace that can write CPU limits, which includes the default `controlledValues: RequestsAndLimits` in every `updateMode` except `Off`, now takes its pods out of Headroom's hands. Switch it to `RequestsOnly` to keep both.
6. **Run the preflight.** `scripts/preflight-namespaces.sh` from this repository exits 1 on a `limits.cpu` ResourceQuota and warns on a LimitRange CPU `max`, `maxLimitRequestRatio` or `default`, in every namespace labelled `kube-headroom.dev/mode=managed`.

If you applied the optional admission policy, re-apply it with `kubectl apply -k config/samples/admission-policy` to get its new rule. Under `Deny` the rule enforces at once.

### Behaviour changes to expect

- **A settings change reaches every affected pod.** `HeadroomConfig` spec changes enqueue every node; a Namespace label or LimitRange change enqueues the nodes holding a pod in that namespace. Each then takes the existing debounce, the per-node rate limit and the client budget. `clientQPS` is not a cluster-wide total, because each REST client gets its own bucket. A reviewer measured 60 nodes of 8 pods on envtest 1.37 at QPS 50, burst 100: one `dryRun` flip made 480 resizes in 8.6s, with 960 PATCH requests averaging 111/s and peaking at 298/s. Q71 tracks whether to share that budget.
- **A refused pod keeps its share while refused.** It stays in the share basis and gets no decision, so neighbours stop at the ceiling they would have if the pod were managed. The slack it holds goes unused until the cause is fixed. An unfixed refusal retries once per `backoffPeriod` even on a quiet node, which is one refused patch, one count and one warning event per pod per minute.
- **Slack now matches what the scheduler books.** Pod overhead and init-container peaks count, so limits drop on nodes with those pods. An init peak stays booked for the pod's whole life, as it does in the scheduler, so that capacity is now idle for bursts too.

### Pods under a VPA

Headroom lists VPAs every 30 seconds, so a new VPA can overwrite a pod's limit once before Headroom steps back. It finds a VPA through the pod's controller and matches by name, so a VPA targeting a custom resource that owns a Deployment is not seen, and a VPA on StatefulSet `dup` also skips Deployment `dup`. A skipped pod keeps whatever limit it had, and nothing marks it once the event expires (Q72). The [tenant guide](https://github.com/karlkfi/kube-headroom/blob/v0.2.0/docs/tenant-guide.md#vpa) has the recipe.

The VPA list is held in memory. On kind, the default 128Mi limit held 20,000 VPAs and 3,000 small pending pods but peaked at up to 122MiB, so raise `resources.limits.memory` before a cluster nears those counts.

### Pods with pod-level resources

Kubernetes 1.35 forbids resizing these pods, because the `InPlacePodLevelResourcesVerticalScaling` gate is off there. The gate is beta from 1.36 ([KEP-5419](https://github.com/kubernetes/enhancements/issues/5419)), and on 1.36.1 and 1.37 any container limit above a pod-level CPU limit is refused. Headroom now leaves these pods alone on every version. Q68 in the [backlog](https://kube-headroom.dev/docs/queue/) tracks returning support.

- **Some have no CPU ceiling.** Without a pod-level CPU limit, a container with no CPU limit stays uncapped, while a plain pod beside it gets a limit. The [runbook](https://github.com/karlkfi/kube-headroom/blob/v0.2.0/docs/runbook.md#limitrange-default) explains that shape and two optional ways to close it: a rule in the admission policy, or a namespace LimitRange default with the side effects it lists. The charts install neither.
- **A pod Headroom already resized keeps that limit until recreated.** Its status annotation goes stale too. On a version where the shrink worked, the pod can stay at a shrunken limit with slack free, or at a high limit on a full node.
- **An empty `resources: {}` is not treated as pod-level resources.** QoS decides that case, and it differs by version: Q69 tracks it.

## Deprecations

None. Nothing in this release is deprecated or removed.

## Known limitations

- **Fractional `maxLimitRequestRatio`: the LimitRange cap is safe rather than tight.** It usually leaves a few millicores unused, but a very small request can hold the whole pod near its request, and a memory-pinned pod can be refused at its QoS floor on every attempt, raising `limitrange-denied`. A whole-number ratio is exact. Q70 tracks the tight cap.
- **A pod already in backoff when its LimitRange is fixed waits out the window**, up to 60s.

## API and surface changes

Diffed between the tags. The `HeadroomConfig` schema, every manager flag, the `kube-headroom.dev/*` keys and all existing metric names and event reasons are unchanged. **Nothing was removed.**

| Surface | Added |
|---|---|
| Metric | `headroom_node_resizes_deferred{node}` |
| `headroom_resizes_total` result | `limitrange-denied`, `forbidden` |
| Event reason | `ResizeLimitRangeDenied`, `VPAManagesLimit` |
| Chart value | `image.digest` |

Three changes keep their names and change meaning:

- `quota-denied` no longer counts other 403s, as **Upgrading** describes.
- `headroom_node_slack_cores` now reports what the scheduler could still place.
- The log line `resize forbidden (likely limits.cpu quota); backing off` is now `resize refused; backing off` with a `refusedBy` field, and refusal event notes quote the API server, truncated to 1024 characters.

## Security

No Headroom advisory accompanies this release. It does carry fixes for advisories in its dependencies, and everyone on v0.1.0 should take them.

Reachability was assessed with call-graph analysis only. `govulncheck` over `./cmd/...` at the v0.1.0 tag, with Go 1.26.5 and that tag's dependencies, reports 22 advisories whose vulnerable symbols the manager can call: 13 in the Go standard library and 9 across `x/net`, `x/text`, grpc and otel. The same tool at this release reports 0. Being callable is not being exploitable, and **nobody assessed whether an attacker could trigger any of them**. For context, the chart's NetworkPolicy limits the metrics port to namespaces labelled `metrics: enabled` and leaves the TLS webhook port open to any source. The scan read source, not the published v0.1.0 binary.
