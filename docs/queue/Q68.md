# Manage pods with pod-level resources where the resize is allowed

**Demand:** someone runs pods with pod-level resources on a version whose `InPlacePodLevelResourcesVerticalScaling` gate is on and wants them shrunk on a full node — or **Event:** Headroom's oldest supported Kubernetes version has that gate on.

Pods with non-empty `spec.resources` are unmanaged on every version, because 1.35 forbids the resize and 1.37 refuses any container limit above the pod-level limit. The cost is on 1.37: measured on kind v1.37.0 before that gate, a pod with 100m of requests shrank to 100m on a full node, and with it the pod stays at 1 CPU.

Managing them needs the pod-level CPU limit as a per-pod cap in the policy, so raises stop at it, and a way to tell whether the server allows the resize at all, such as the server version or a classified refusal. Neither has been built or measured.
