# Manage pods with pod-level resources where the resize is allowed

**Demand:** someone runs pods with pod-level resources on a version whose `InPlacePodLevelResourcesVerticalScaling` gate is on and wants them shrunk on a full node — or **Event:** Headroom's oldest supported Kubernetes version has that gate on.

Pods with non-empty `spec.resources` are unmanaged on every version, because 1.35 forbids the resize and 1.37 refuses any container limit above the pod-level limit. The cost is on 1.37: measured on kind v1.37.0 before that gate, a pod with 100m of requests shrank to 100m on a full node, and with it the pod stays at 1 CPU.

The cap half already exists. The reviewer of the change that excluded them took the smaller of `UserCapMilli` and `spec.resources.limits.cpu` in `buildPodInput`, with the gate removed, and on envtest 1.37 passes returning an error while raising fell from 13 of 14 to 0 of 14. No kubelet was involved.

The open part is telling whether the server allows the resize at all, such as from the server version. The 1.35 refusal reads `is invalid` rather than forbidden, so it takes the generic error path. Also, where the API server fills in the pod-level limit, the first limit set becomes the ceiling, so such a pod could only shrink below that first value (measured by the same reviewer: a pod born at 110m could not go above 110m). None of this has been built.
