# Cap raises at a namespace LimitRange instead of failing them

A LimitRange maximum blocks a raise outright, where the runbook promises raises "just stop at the cap". The controller then blames a ResourceQuota, which points the operator at the wrong object.

Measured 2026-11-04 on a kind v1.35.0 cluster (worker with 18 allocatable CPUs), image built from 1be389d, webhooks off. With a container `max` of 500m, a pod with request 100m and limit 200m, and a computed target of 1000m, the limit stayed at 200m instead of reaching 500m. The controller logged this twice, 88 seconds apart, the second time only after a pod event:

```text
resize forbidden (likely limits.cpu quota); backing off
pods "d1" is forbidden: maximum cpu usage per Container is 500m, but limit is 1
```

The value of `headroom_resizes_total` was not read, because the metrics proxy request failed. From the code, this refusal increments `result="quota-denied"`.

Read LimitRanges into the clamp step, as design section 8.3 calls for, so the target stops at the cap. Then separate a LimitRange refusal from a quota refusal in the log, event and metric. Add an e2e spec for both, and correct the runbook once the behaviour matches.

The RBAC for LimitRanges is already granted and nothing uses it. `internal/eligibility/eligibility.go:127:LimitRange awareness is deferred to Phase 2`, `internal/controller/node_controller.go:376:likely limits.cpu quota` and `docs/runbook.md:44:just stop at the cap` are the sites.
