# Resize native sidecars through initContainers, not containers

A managed pod with a native sidecar that requests CPU never gets resized, and it fails with an error on every pass. The controller's resize patch lists every resizable container under `spec.containers`, but a native sidecar lives under `spec.initContainers`, so the API server reads it as an added container and refuses the whole patch.

Measured 2026-11-05 on a kind v1.35.0 cluster (worker with 18 allocatable CPUs), image built with webhooks off from the branch that keeps a node's pass going past a failed pod. A pod named `a-sidecar` (app 100m request and 1 CPU limit, sidecar 20m request and 200m limit) shared a full node with six other managed pods. After 100 seconds it was still at 1 CPU while the other six had shrunk, and the controller had logged 15 reconcile errors, each ending:

```
Pod "a-sidecar" is invalid: [spec.containers[1].image: Required value, spec.initContainers[0].name: Duplicate value: "side", spec.containers: Forbidden: containers may not be added or removed on resize]
```

envtest 1.37 refuses the same patch, so a spec there can pin the fix. Existing specs miss this because `makeBurstablePodWithSidecar` builds its sidecar as a second app container. `docs/design.md:108:Sidecar containers can.` promises that these resize.

Send restartable init containers under `spec.initContainers` in the patch body. Only the refused patch and the log were measured; whether the sidecar then resizes on a real node has not been tried, so check it on kind.

`internal/controller/node_controller.go:355:"spec": map[string]any{"containers": containers},` is the patch body.
