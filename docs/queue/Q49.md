# Let full nodes shrink pods whose memory request equals their limit

When a node has no slack, a pod whose memory request equals its memory limit keeps its old CPU limit, and the error stops the rest of that node's pass. Setting the CPU limit equal to the request would make such a pod Guaranteed, and the API server refuses any resize that changes QoS class. This pod shape is common, and the failure lands exactly when the node is contended.

Measured 2026-11-04 on a kind v1.35.0 cluster (worker with 18 allocatable CPUs), image built from 1be389d, webhooks off. Three pods with memory requests equal to limits and three plain pods (CPU request 100m each) shared a node, then a filler pod took the remaining 17290m. After 100 seconds:

- `memeq1`, `memeq2` and `memeq3` were still at a 1 CPU limit (target 100m), with `Pod QOS Class may not change as a result of resizing` in the log.
- `plain1` and `plain2` had shrunk to 100m.
- `plain3`, which nothing is wrong with, stayed at 1 CPU with a stale status annotation (slack 17290m), because the error aborted the pass before reaching it.
- The controller logged 15 reconcile errors, and the state never converged.

Two changes are needed. Floor the target above the request for any pod that the collapse would turn Guaranteed; one quantum is the likely floor, but it has not been designed or tested. And stop one pod's refused resize from ending the pass for the rest of the node.

The fake-client unit tests cannot see this refusal, so add coverage against a real API server. e2e can do it; whether the envtest API server enforces the same check is unverified.

`docs/design.md:106:QoS class is immutable.` names the constraint. `internal/policy/policy.go:115:collapse to request` is the collapse, and `internal/controller/node_controller.go:237:fmt.Errorf("resize %s: %w", d.Key, err)` is the abort.
