# Count init containers and pod overhead in node slack

Slack may be overstated compared with the scheduler, because it sums only app and sidecar requests. The scheduler also counts regular init containers (each pod's effective request is the larger of the two) and pod overhead, so a node it treats as full could still show slack here, and limits would be raised on it.

This comes from reading the code and has not been reproduced. Start with a failing test: a pod whose init container requests more than its app containers, and a pod with `RuntimeClass` overhead, compared with what the scheduler reports. The effect is probably small on most nodes, so check the size before reranking.

`internal/eligibility/eligibility.go:52:Restartable-init (native sidecar) containers` is where only sidecars are admitted to the sum.
