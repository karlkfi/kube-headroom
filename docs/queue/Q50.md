# Apply config, enrollment and pod setting changes on quiet nodes

Flipping `dryRun` to false, enrolling a namespace or capping a running pod does nothing until another pod lands on that node. Runbook step 3 flips `dryRun` and says "Now watch", so an operator following the staged rollout sees nothing happen and has no signal why.

Measured 2026-11-04 on a kind v1.35.0 cluster (worker with 18 allocatable CPUs), image built from 1be389d, webhooks off.

- **Flip `dryRun` to false:** the pod had no limit at +15s, +60s and +120s, then got a 1 CPU limit once an unrelated pod landed.
- **Label a namespace whose pods are already running:** no limit or annotation after 60 seconds, then a limit once an unrelated pod landed.
- **Add `kube-headroom.dev/max-cpu=300m` to a running pod:** still 1 CPU after 45 seconds, then 300m once an unrelated pod landed.
- **Opt-out label on a running pod:** not tested. The code suggests the same behaviour.

Read from the code and not run: a pod in backoff is not requeued when the backoff expires, so on a quiet node it waits for the next pod event too. The LimitRange test in Q52 shows retries happening only after a pod event.

The controller watches only Pod and Node, and its pod predicate ignores label and annotation changes. Add `HeadroomConfig` and Namespace watches that enqueue the affected nodes, let the pod predicate pass the labels and annotations the controller reads, and requeue when a backoff expires. The design scopes recomputation to scheduling events, so `docs/design.md` needs updating to match.

e2e misses this because it applies the config before creating pods. Add one spec per trigger, with pods already running and no pod event afterwards.

`internal/controller/node_controller.go:725:Watches(&corev1.Pod{}, r.podEventHandler(),`, `internal/controller/node_controller.go:762:func podUpdateRelevant` and `docs/design.md:214:Events that enqueue a node key` are the places to start.
